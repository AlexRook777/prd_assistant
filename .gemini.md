# PRD Assistant - Payment Integration System

## Project Purpose
This project is **exclusively** for payment integration research and development following the **PRD-First** methodology. We process 3-4 new payment provider integrations daily, requiring:
- Rapid workspace setup from templates
- Step-by-step execution control (Jupyter Notebook style)
- Consistent application of business rules across all integrations

## Execution Style: Jupyter Notebook Mode
The user works in an iterative, exploratory style:
- **Step-by-step execution**: User can execute individual workflow steps (e.g., `/step1-epic-analysis`)
- **Iterative refinement**: User may re-run specific steps multiple times until results are satisfactory
- **Phase-level automation**: User can also request full-phase execution (e.g., `/phase1-full`)
- **Always wait for confirmation**: Never auto-proceed between different phases without user approval

## Hierarchy of Truth
When encountering conflicting information, apply this **Order of Precedence**:

1. **Per-Integration `project_rules.md`**: Integration-specific overrides (highest priority if file exists)
2. **Rulebook (BetterBro)**: Internal protocol standards (see below)
3. **Master PRD Schema**: Structural template at `.master_prd/master_prd.yaml`
4. **Provider Documentation**: External docs are "claims" that must be verified via testing
5. **Agent Prompts/Workflows**: Execution guidance (lowest priority)

## BetterBro Standards

### Core Principles
- **Clarity**: All endpoints must be documented with clear descriptions of request and response fields
- **Consistency**: Use standard naming conventions (snake_case for JSON keys)
- **Error Handling**: Standardized error codes and messages must be used
- **Security**: All integrations must follow the security protocols defined in the global security policy

### Integration Standards
- **H2H (Host-to-Host)** is preferred over Redirects unless specified
- **PIX payments** should be treated as dynamic QR codes
- **Webhooks** must be authenticated
- **Field Mapping**: Every external API field must be mapped to an internal "home" defined in BetterBro standards

## PRD-First Development Principles

### What is PRD-First?
PRD-First Development is the core methodology of this system. Requirements are **fully defined, validated, and documented** before any implementation begins. This "Source of Truth" approach is critical for maintaining consistency in agentic workflows.

### Core Principles
1. **PRD as the Source of Truth**: The PRD is not just a document; it is the definitive specification for the integration. Any discrepancy between code and PRD must be resolved in favor of the PRD.
2. **Agent Alignment**: Agents must consume the PRD to understand context, constraints, and business logic before generating code or performing mappings.
3. **Architecture Before Implementation**: All technical components (endpoints, field mappings, state flows) must be architected in the PRD phase.
4. **Validation-Driven**: Every integration must be validated against the PRD structure defined in `.master_prd/master_prd.yaml`.
5. **Living Document**: The PRD is updated as new edge cases are discovered during the integration process, ensuring documentation never falls behind implementation.

### PRD-First Workflow Sequence
1. **Discovery**: Analyze provider documentation
2. **Drafting**: Create initial PRD using the global template
3. **Refinement**: Apply local rules and BetterBro standards to the PRD
4. **Finalization**: Approve the PRD as the immutable specification for implementation

## Master PRD Schema
**Location**: `.master_prd/master_prd.yaml`

This YAML file defines the canonical structure for all integration PRDs. It specifies required sections like:
- Project Overview
- Technical Specifications (API Endpoints, Authentication)
- User and Data Flows (with Mermaid diagrams)
- Field Mapping Tables
- Testing and Validation Requirements

All generated PRDs must conform to this schema.

## Integration Workspace Structure

Every integration in `/integrations/<Integration_Name>/` follows this **mandatory** structure:

```
/integrations/<Integration_Name>/
├── 0_initial_docs/      # Raw documentation (IMMUTABLE)
│   └── [Epic/Jira requirements, provider API docs, PDFs, etc.]
├── 1_research/          # Phase 1 Research outputs (7 files)
│   ├── 1.epic_analysis.md
│   ├── 2.docs_analysis.md
│   ├── 3.local_test_page.md
│   ├── 3.test_page.html
│   ├── 4.access_and_fields.md
│   ├── 5.compatibility.md
│   ├── 6.project_stories.md
│   └── 7.field_testing.md
├── 2_development/       # Phase 2 Development outputs
│   └── 8.balance_retrieval.md
├── 4_test/              # Phase 4 QA outputs
├── config               # Credentials, API URLs (UNIQUE per integration)
└── project_rules.md     # Integration-specific overrides (OPTIONAL)
```

### Critical Working Directory Rules
Each phase's agent must operate **exclusively** within its assigned subfolder to maintain strict context boundaries and prevent file pollution:
- Research Agent → `1_research/` folder only
- Development Agent → `2_development/` folder only
- Test Agent → `4_test/` folder only

### Configuration (`config`)
Instead of searching for keys in scattered files, look for a `config` file in the root of the integration workspace.

**ALWAYS** read the local `config` file at the start of any integration work.

### Integration `config` File
Every integration has a `config` file containing *specific* credentials and endpoints:
- `PROVIDER_API_DOCUMENTATION_URL`: Link to provider's official API docs
- `CLIENT_ID`, `CLIENT_SECRET`: Provider credentials
- `API_ENDPOINT`: Provider's base API URL (if needed)

**ALWAYS** read both `global_config` and the local `config` file at the start of any integration work.

### Integration `project_rules.md` (Optional)
If this file exists in an integration folder, it **overrides** global rules for that specific integration. Use it for:
- Provider-specific quirks (e.g., "This provider requires ISO-8859-1 encoding")
- Custom workflow deviations (e.g., "Skip Step 5 for this integration")
- Temporary exceptions

## Context Management Principles

To prevent **Context Rot**:
- **Reduce**: Use high-signal bullet points when summarizing findings
- **Isolate**: If generating UML diagrams, create them separately to avoid polluting mapping logic context
- **Pin**: At the start of a new integration, pin `.master_prd/` files and the integration's `0_initial_docs/` to your static buffer

## New Integration Initialization

When starting a new integration:
1. **Copy Template**: Duplicate `/integrations/_TEMPLATE/` to `/integrations/Integration_<ProviderName>/`
2. **Populate Initial Docs**: Place Epic/Jira requirements and provider documentation in `0_initial_docs/`
3. **Fill Config**: Update the `config` file with API credentials and documentation URL
4. **Read Context**: Load `0_initial_docs/` and local `config` file
5. **Execute Workflows**: Begin with `/step1-epic-analysis` or `/phase1-full`

## Workflow Invocation Pattern

Workflows are available in `.agent/workflows/` and can be invoked via slash commands:

**Individual Steps** (Jupyter-style):
- `/step1-epic-analysis` → Execute only Step 1
- `/step2-doc-and-api-analysis` → Execute only Step 2
- `/step3-create-test-page` → Execute only Step 3 (triggers test_page_generator skill)
- ... (steps 4-7)

**Full Phases**:
- `/phase1-full` → Execute all 7 research steps sequentially
- `/phase2-full` → Execute development phase
- `/phase4-full` → Execute testing phase

## Skills Auto-Detection

Skills in `.agent/skills/` are automatically triggered by context. For example:
- **test_page_generator**: Activated when user mentions "create test page" or invokes Step 3 of research

Do NOT manually reference skills unless debugging; let Antigravity auto-detect when to use them.

## Agent Directives

- **Never** create files outside the designated phase folder
- **Always** verify `config` file exists and is populated before starting work
- **Always** check for `project_rules.md` in the integration folder — if it exists, it overrides these global rules
- **Document everything**: Every step produces a markdown file with clear sections
- **Test before documenting**: For Step 3 (test page), actually run the test page and include screenshots/logs in the documentation


## Presentation Rules
- **Markdown Files**: MUST always be presented or opened in **Rendered/Preview Mode** (Final View), NEVER in Raw/Source mode.
