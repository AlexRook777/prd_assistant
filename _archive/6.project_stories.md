# Epic: SmartFastPay Ecuador USD Payin HPP
**Goal**: Integrate SmartFastPay as a provider for Bank Transfers in Ecuador (USD) using a Hosted Payment Page (HPP) flow.

## Story 1: Authorization
### Description
As a System, I want to authenticate with the SmartFastPay API so that I can perform secure transactions.

### Technical Specifications
*   **Method**: `POST /oauth2/token`
*   **Base URL**: `https://sandbox.smartfastpay.com` (Sandbox) / `https://api.smartfastpay.com` (Live)
*   **Headers**: 
    - `Authorization: Basic [Base64(client_id:client_secret)]`
    - `Content-Type: application/x-www-form-urlencoded`
*   **Body (Form Data)**: `grant_type=client_credentials`
*   **Token Refresh**: Tokens are valid for 3600 seconds. A new token should be requested upon expiration.

### Acceptance Criteria

**Scenario: Successful Token Generation**
*   [x] **Given** Valid client credentials for the environment
*   [x] **When** I request an access token from the token endpoint
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The response contains an `access_token` and `token_type: "Bearer"`

**Scenario: Invalid Credentials**
*   [x] **Given** Invalid client_id or client_secret
*   [x] **When** I request an access token
*   [x] **Then** I receive a 200 OK response with an `INVALID_CLIENT` error code in the `moreInformation` block

## Story 2: Payin Transaction Creation (HPP)
### Description
As a Merchant, I want to create a checkout session so that my customer can be redirected to the provider's payment page.

### Technical Specifications
*   **Endpoint**: `POST /v2/transaction/checkout`
*   **Method**: POST
*   **Authentication**: Bearer Token
*   **Request Mapping (BetterBro -> Provider)**:
    - `external_transaction_id` -> `transaction.id`
    - `amount / 100` -> `transaction.amount` (BetterBro integer to Provider decimal)
    - `amount_currency` -> `transaction.currency` (USD)
    - `external_customer_id` -> `customer.id`
    - `fields.first_name` + `fields.last_name` -> `customer.name`
    - `fields.email` -> `customer.email`
    - `fields.tax_id` -> `customer.tax_id`
    - `fields.tax_id_type` -> `customer.tax_id_type` (CI, RUC, PASS)
    - `point.callback_url` -> `notification_url`
    - `point.return_url` -> `redirect_url`
*   **Fixed Parameters**:
    - `country`: `ECU` (Provider requires alpha-3)
    - `payment_method`: `["bank_transfer"]`

### Acceptance Criteria

**Scenario: Successful Checkout Creation**
*   [x] **Given** Valid Ecuador customer data, USD currency, and amount within limits ($6 - $1000)
*   [x] **When** I send a POST request to `/v2/transaction/checkout`
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The response contains a `url` (Checkout URL)
*   [x] **And** The response contains a provider `transaction_id`

**Scenario: Missing Mandatory Field**
*   [x] **Given** A request missing `transaction.id`
*   [x] **When** I send a POST request to `/v2/transaction/checkout`
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The `moreInformation` block contains the error code `INVALID_REQUEST`
*   [x] **And** The detail message mentions the missing field

## Story 3: Webhook Notification Handling
### Description
As a System, I want to process webhook notifications from SmartFastPay so that the transaction status is updated automatically.

### Technical Specifications
*   **Endpoint**: POST to `notification_url`
*   **Authentication**: Signature verification (HMAC-SHA256) using `X-Signature` header.
*   **Status Mapping (Provider -> BetterBro)**:
    - `pending` -> `3 PENDING`
    - `paid` -> `1 SUCCESS`
    - `denied` -> `2 FAILED`
    - `expired` -> `2 FAILED`

### Acceptance Criteria

**Scenario: Process "paid" Webhook**
*   [ ] **Given** A valid incoming webhook for a successful payment (`status: "paid"`)
*   [ ] **When** The system verifies the signature and parses the payload
*   [ ] **Then** The internal transaction status is updated to `1 SUCCESS`
*   [ ] **And** The system returns a 200 OK to the provider

**Scenario: Process "denied" Webhook**
*   [ ] **Given** A valid incoming webhook for a failed payment (`status: "denied"`)
*   [ ] **When** The system verifies the signature and parses the payload
*   [ ] **Then** The internal transaction status is updated to `2 FAILED`

**Scenario: Invalid Webhook Signature**
*   [ ] **Given** An incoming webhook with an invalid `X-Signature`
*   [ ] **When** The system attempt to verify the signature
*   [ ] **Then** The request is rejected (e.g., 401/403) and no status update occurs

## Story 4: Transaction Status Inquiry
### Description
As a System, I want to manually check the status of a transaction if webhooks are delayed or missing.

### Technical Specifications
*   **Endpoint**: `GET /v2/transaction/{id}`
*   **Method**: GET
*   **Authentication**: Bearer Token

### Acceptance Criteria

**Scenario: Check Status of Existing Transaction**
*   [ ] **Given** A valid provider transaction ID
*   [ ] **When** I send a GET request to `/v2/transaction/{id}`
*   [ ] **Then** I receive a 200 OK response
*   [ ] **And** The response data contains the current `status` (e.g., `paid`)

---

## Story 5: Regional Validation (Ecuador)
### Description
As a System, I want to ensure that Ecuador-specific field requirements are met to avoid provider-side rejections.

### Technical Specifications
*   **Validation Rules**:
    - `tax_id_type` MUST be CI, RUC, or PASS for country ECU.
    - `tax_id` must match the expected format for the selected type.
*   **Mapping**: Map BetterBro `customer.document` structure to provider's flat `customer.tax_id` fields.

### Acceptance Criteria

**Scenario: Invalid Ecuador Document Type**
*   [x] **Given** A transaction for country `ECU`
*   [x] **When** The document type is not "CI", "RUC", or "PASS" (e.g. "ID")
*   [x] **Then** The system receive a 200 OK response with `INVALID_REQUEST` error detail "Document type ... not found"

**Scenario: Validating Amount Limits**
*   [ ] **Given** An amount of $5 (below $6 minimum)
*   [ ] **When** I attempt to create a transaction
*   [ ] **Then** The request is rejected with a validation error
