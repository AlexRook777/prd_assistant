# Epic: SmartFastPay Ecuador USD Payin HPP
**Goal**: Integrate SmartFastPay for Bank Transfer (Payin) in Ecuador using the HPP (Checkout) flow, ensuring compatibility with the BetterBro standard.

## Story 1: Authorization
### Description
As a System, I want to authenticate with the SmartFastPay API using OAuth 2.0 to obtain a Bearer token for secure requests.

### Technical Specifications
*   **Method**: `POST`
*   **Endpoint**: `https://api.smartfastpay.com/oauth2/token` (Production) / `https://sandbox.smartfastpay.com/oauth2/token` (Sandbox)
*   **Headers**: 
    *   `Authorization: Basic <base64(client_id:client_secret)>`
    *   `Content-Type: application/x-www-form-urlencoded`
*   **Body**: `grant_type=client_credentials`
*   **Response**: 
    ```json
    {
      "data": {
        "access_token": "...",
        "token_type": "Bearer",
        "expires_in": 3600
      }
    }
    ```

### Acceptance Criteria

**Scenario: Successful Token Generation**
*   **Given** Valid client credentials and a functional sandbox environment
*   **When** I request an access token with `grant_type=client_credentials`
*   **Then** I receive a 200 OK response
*   **And** The response contains an `access_token`
*   **And** The token type is `Bearer`

**Scenario: Invalid Credentials**
*   **Given** An invalid client_id or secret
*   **When** I request an access token
*   **Then** I receive a 401 Unauthorized response
*   **And** The error detail indicates invalid credentials

## Story 2: PayIn Transaction Creation (HPP)
### Description
As a Merchant, I want to create a payment session so my customer can be redirected to the SmartFastPay checkout page.

### Technical Specifications
*   **Method**: `POST`
*   **Endpoint**: `/v2/transaction/checkout`
*   **BetterBro Mappings**:
    *   `amount`: BetterBro Integer (cents) -> SmartFastPay Decimal (`BetterBro / 100`).
    *   `country`: BetterBro `EC` -> SmartFastPay `ECU`.
    *   `tax_id_type`: BetterBro `CI` -> SmartFastPay `CC` (for Cedula Ciudadania).
*   **Required Fields**:
    *   `customer.id`, `customer.name`, `customer.email`, `customer.document.number`, `customer.document.type` (CC).
    *   `transaction.id`, `transaction.currency` (USD), `transaction.amount`.
    *   `country` (ECU), `payment_method` (["bank_transfer"]), `notification_url`, `redirect_url`.

### Acceptance Criteria

**Scenario: Successful HPP Session Creation**
*   **Given** A valid access token and customer data for Ecuador
*   **When** I send a POST request to `/v2/transaction/checkout` with amount 10.00 and currency USD
*   **Then** I receive a 200/201 OK response
*   **And** The response contains a redirection `url` in `data.url`
*   **And** The response contains a provider `transaction_id`

**Scenario: Validation Error (Missing Field)**
*   **Given** A request missing the `notification_url`
*   **When** I send the POST request
*   **Then** I receive a 400 Bad Request
*   **And** The `moreInformation` block contains `INVALID_REQUEST` for the missing field

## Story 3: Webhook Handling
### Description
As a System, I want to process incoming status updates from SmartFastPay to update the internal transaction status.

### Technical Specifications
*   **Method**: `POST`
*   **Status Mapping**:
    *   `paid` -> `1 SUCCESS`
    *   `denied` -> `2 FAILED`
    *   `pending` -> `10 PENDING`
    *   `expired` -> `5 EXPIRED`
*   **Verification**: Implement HMAC SHA256 signature verification (if provided by provider) or verify source IP.

### Acceptance Criteria

**Scenario: Processing "Paid" Notification**
*   **Given** A pending transaction with external_id `TX_123`
*   **When** SmartFastPay sends a POST notification with `status: "paid"` and `transaction_id: "TX_123"`
*   **Then** The internal system updates the transaction status to `SUCCESS` (Code 1)
*   **And** The system acknowledges the webhook with a 200 OK

**Scenario: Processing "Denied" Notification**
*   **Given** A pending transaction
*   **When** A notification with `status: "denied"` is received
*   **Then** The internal system updates the transaction status to `FAILED` (Code 2)

## Story 4: Transaction Status Check (Polling)
### Description
As a System, I want to manually query the status of a transaction to ensure synchronization in case webhooks are delayed.

### Technical Specifications
*   **Method**: `GET`
*   **Endpoint**: `/v2/transaction/{transaction_id}`
*   **Parameters**: `{transaction_id}` refers to the provider's internal ID returned during creation.

### Acceptance Criteria

**Scenario: Polling Successful Transaction**
*   **Given** A transaction previously created with ID `TX_999`
*   **When** I send a GET request to `/v2/transaction/TX_999`
*   **Then** I receive a 200 OK response
*   **And** The response contains the current `status` (e.g., `paid` or `pending`)

---

## Story 5: Error Handling & BetterBro Mapping
### Description
As an Adapter, I want to normalize provider responses and errors to the BetterBro standard.

### Technical Specifications
*   **Field Normalization**:
    *   Convert `10.00` decimal to `1000` integer.
    *   Ensure document types are mapped correctly before sending to provider.
*   **Error Mapping**:
    *   `INVALID_REQUEST` -> `BAD_REQUEST`
    *   `AUTHENTICATION_ERROR` -> `UNAUTHORIZED`

### Acceptance Criteria

**Scenario: Amount Normalization**
*   **Given** A BetterBro request with amount `5000` (50.00 USD)
*   **When** The adapter prepares the payload for SmartFastPay
*   **Then** The amount field in the payload is set to `50.00` (decimal)

**Scenario: Document Type Mapping**
*   **Given** A BetterBro request with `tax_id_type: "CI"` for Ecuador
*   **When** The adapter prepares the payload
*   **Then** the document type is sent as `CC` to SmartFastPay

---

## Workflow Suggestions

- **Mapping Tests**: Ensure unit tests cover the `CC` <-> `CI` conversion specifically for the Ecuador region.
- **Rounding Logic**: Use strict rounding to two decimal places when converting BetterBro integers to SmartFastPay decimals to avoid floating point issues.
- **Polling Fallback**: Implement polling triggered 5 minutes after HPP creation if no webhook is received.
