# Epic: SmartFastPay Ecuador - USD - Bank Transfer Payin HPP
**Goal**: Integrate SmartFastPay to support USD Bank Transfer Payins in Ecuador via Hosted Payment Page (HPP).

## Story 1: Authorization
### Description
As a System, I want to authenticate with the SmartFastPay API using OAuth 2.0 so that I can securely perform transaction operations.

### Technical Specifications
*   **Endpoint**: `POST /oauth2/token`
*   **Method**: `POST`
*   **Headers**: 
    - `Content-Type: application/json`
*   **Body**: 
    ```json
    {
      "grant_type": "client_credentials",
      "client_id": "...",
      "client_secret": "..."
    }
    ```
*   **CORS Support**: Not required for S2S calls; handled via local proxy in test environment.

### Acceptance Criteria

**Scenario: Successful Token Generation**
*   [x] **Given** Valid `client_id` and `client_secret`
*   [x] **When** I send a POST request to `/oauth2/token`
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The response contains an `access_token`
*   [x] **And** The token type is `Bearer`

**Scenario: Invalid Credentials**
*   [ ] **Given** Invalid `client_id` or `client_secret`
*   [ ] **When** I send a POST request to `/oauth2/token`
*   [ ] **Then** I receive a 401 Unauthorized response
*   [ ] **And** The response contains an `error` field explaining the failure

---

## Story 2: PayIn Transaction Creation (HPP)
### Description
As a Merchant, I want to initiate a PayIn transaction and receive a payment URL so that I can redirect my customer to complete the bank transfer.

### Technical Specifications
*   **Endpoint**: `POST /v2/transaction/checkout`
*   **Method**: `POST`
*   **Payload (BetterBro Optimized)**:
    - `transaction.id`: external transaction ID
    - `transaction.amount`: float (e.g., 10.00)
    - `transaction.currency`: "USD"
    - `customer.document.type`: "CI", "RUC", "PASS"
    - `payment_method`: ["bank_transfer"]
*   **Response**: `data.url` (Redirect URL), `data.transaction_id` (Provider ID)

### Acceptance Criteria

**Scenario: Successful Payment Link Generation**
*   [x] **Given** A valid access token
*   [x] **And** Valid customer email and document number
*   [x] **And** Amount is within limits (6 - 1,000 USD)
*   [x] **When** I send a POST request to `/v2/transaction/checkout`
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The response contains a `url` starting with `https://sandbox-checkout.smartfastpay.com`
*   [x] **And** The transaction status in provider system is `open`

**Scenario: Validation Error - Missing Required Field**
*   [ ] **Given** A request missing the `customer.email` field
*   [ ] **When** I send a POST request to `/v2/transaction/checkout`
*   [ ] **Then** I receive a 400 Bad Request response
*   [ ] **And** The response body contains details about the missing field

## Story 3: Transaction Status Check (Polling)
### Description
As a System, I want to poll the status of a transaction so that I can update the internal state even if the webhook is delayed.

### Technical Specifications
*   **Endpoint**: `GET /v2/transaction/{transaction_id}`
*   **Method**: `GET`
*   **Response Mapping**:
    - `open` -> `10 PENDING`
    - `paid` -> `1 SUCCESS`
    - `cancelled` -> `3 CANCELLED`

### Acceptance Criteria

**Scenario: Get Status Success**
*   [x] **Given** A valid provider `transaction_id`
*   [x] **When** I send a GET request to `/v2/transaction/{id}`
*   [x] **Then** I receive a 200 OK response
*   [x] **And** The response contains the `status` field
*   [x] **And** The `amount` matches the original request

**Scenario: Transaction Not Found**
*   [ ] **Given** A non-existent `transaction_id`
*   [ ] **When** I send a GET request to `/v2/transaction/invalid_id`
*   [ ] **Then** I receive a 404 Not Found response

---

## Story 4: Webhook Handling
### Description
As a System, I want to receive asynchronous notifications from SmartFastPay so that I can automatically confirm payments in real-time.

### Technical Specifications
*   **Endpoint**: Merchant-defined `notification_url`
*   **Verification**: `X-Signature` header (HMAC SHA-256)
*   **Payload Structure**:
    ```json
    {
      "transaction_id": "...",
      "status": "paid",
      "amount": 10.00,
      "id": "order_..."
    }
    ```

### Acceptance Criteria

**Scenario: Process Valid 'Paid' Webhook**
*   [ ] **Given** A valid incoming POST request with a correct `X-Signature`
*   [ ] **And** The payload status is `paid`
*   [ ] **When** The system processes the webhook
*   [ ] **Then** The internal transaction status is updated to `1 SUCCESS`
*   [ ] **And** The system returns a 200 OK to the provider

**Scenario: Invalid Webhook Signature**
*   [ ] **Given** An incoming webhook with a signature that does not match the payload
*   [ ] **When** The system attempts to verify the request
*   [ ] **Then** The system returns a 403 Forbidden or 401 Unauthorized
*   [ ] **And** The transaction status remains unchanged

---

## Story 5: Error Handling & Validation
### Description
As a User, I want to see meaningful error messages when a transaction fails so that I can correct my input.

### Technical Specifications
*   **Map error codes**:
    - `OUT_OF_LIMITS` -> "Amount must be between 6 and 1000 USD"
    - `INVALID_DOCUMENT` -> "The provided document number is invalid for Ecuador"

### Acceptance Criteria

**Scenario: Handle Amount Below Minimum**
*   [ ] **Given** An amount of 5.00 USD
*   [ ] **When** I attempt to create a transaction
*   [ ] **Then** The system prevents the request
*   [ ] **And** Displays "Amount must be between 6 and 1000 USD"

**Scenario: Provider System Error**
*   [ ] **Given** The provider API is down (returns 500 status)
*   [ ] **When** I attempt any API operation
*   [ ] **Then** The system logs the error
*   [ ] **And** Returns a `PROVIDER_ERROR` status internally

---

## Workflow Suggestions
1. **Signature Verification**: Prioritize the implementation of HMAC verification logic as it is the most common point of failure in webhook integrations.
2. **Limit Synchronization**: Keep the 6-1000 USD limits in a configuration file rather than hardcoded to allow quick adjustments if the provider's policy changes.
3. **Polling Strategy**: Implement exponential backoff for status polling to avoid unnecessary API load while ensuring timely updates.
