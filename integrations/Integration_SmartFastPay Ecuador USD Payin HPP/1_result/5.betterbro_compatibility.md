# BetterBro Compatibility Report

**Date**: 2026-02-12

## 1. Rulebook Identification
- **Selected Rule**: Acquiring Form
- **Service Instance**: Ecuador Bank Transfer Payin HPP
- **Provider Service URL**: [SmartFastPay API (v2)](https://smartfastpay.com/api-v2-en/checkout/payin-checkout)
- **BetterBro Service URL**: [https://docs.betterbro.com/services/ecuador/bank_transfer/payin_hpp](https://docs.betterbro.com/services/ecuador/bank_transfer/payin_hpp)
- **Confidence**: High
- **Rationale**: The SmartFastPay integration is a classic HPP (Hosted Payment Page) flow where a transaction is created server-side and the user is redirected to a `pay_url`. This perfectly aligns with the BetterBro "Acquiring Form" standard.

## 3. Status Mapping (The "Rosetta Stone")
| Provider Status | 4bill Internal Code | Logic/Rule |
| :--- | :--- | :--- |
| `open` | `10 PENDING` | Transaction created, waiting for consumer action. |
| `paid` | `1 SUCCESS` | Payment successfully confirmed. |
| `cancelled` | `3 CANCELLED` | User explicitly cancelled the transaction. |
| `expired` | `5 EXPIRED` | Transaction lifetime (10 mins) exceeded. |
| `failed` | `2 FAILED` | Technical failure or bank rejection. |

**Ambiguous Statuses**:
- None. SmartFastPay statuses map directly to BetterBro standard event codes.

## 4. Automation & Logic
- **Architecture Type**: HPP (Redirect)
- **Deterministic**: Yes. The flow is state-machine compliant.
- **Webhooks**: Standard JSON POST callbacks with HMAC SHA-256 signature verification.

## 5. Blocking Issues & Risks
- [RISK] **Amount Normalization**: The transition from float (Provider) to integer cents (BetterBro) must be handled with precision to avoid rounding errors.
- [RISK] **Name Splitting**: If the upstream system only provides a single `name` field, we may need to implement a simple split logic to populate BetterBro's `first_name`/`last_name` if both are explicitly required by the final implementation.

## 6. Recommendation
- [x] **GREEN LIGHT**: Fully compatible, proceed to implementation.
- [ ] **YELLOW LIGHT**: Minor custom logic needed, proceed with caution.
- [ ] **RED LIGHT**: Major architectural blocker, STOP and discuss.

## Workflow Suggestions
1. **Schema Validation**: During Step 7 (Contract Spec), strictly enforce the integer conversion for the `amount` field.
2. **Webhook Verification**: Ensure the `X-Signature` logic is explicitly documented to match BetterBro's standard implementation.
